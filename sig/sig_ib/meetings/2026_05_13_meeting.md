### 议题1、construction_ai_vision（施工AI视觉检测）建仓
#### 汇报人：宋正伟
**1、仓库更名与定位**

宋正伟说明，原“施工安全监控代码仓”按算法功能更名为 `construction_ai_vision`，定位为面向OpenHarmony边缘设备的施工现场目标检测仓，支持单张图片检测与视频流实时检测、边缘端本地推理，并提供可视化应用。

**2、检测类别（共37类）**

| 类别 | 具体目标 |
| :--- | :--- |
| 人员安全（6类） | 人员、安全帽、反光衣、手套、面罩、安全带 |
| 施工机械（16类） | 挖掘机、推土机、轮式起重机、塔吊、叉车、装载机、压路机、混凝土泵车、旋挖钻机、平地机、沥青摊铺机、路面切割机、机械臂、重型机械、汽车、卡车 |
| 工具设备（9类） | 电钻、电镐、电锯、电焊、短柄工具、长柄工具、绳索、料桶、切割设备、泵管 |
| 场地设施（6类） | 手推车、梯子、脚手架、配电箱、物料 |

**3、模型选型**

| 模型 | 参数量 | 特点与使用场景 |
| :--- | :--- | :--- |
| YOLOv5n | 约1.8M | 超轻量级，适合资源受限边缘设备（如HH-SCDAYU200）及视频流检测 |
| YOLOv8n | 约3.2M | 轻量化、精度优于v5n，适合边缘设备及视频流检测 |
| YOLOv8s | 约11.2M | 精度更高，可端侧部署，更适合服务器端或高性能设备 |

**4、训练与端侧部署链路（OpenHarmony）**

会议明确所有训练任务在 `yolo-train/` 目录下完成，统一模型转换与部署链路：
- Windows环境训练Ultralytics官方YOLOv5、v8等模型，得到 `.pt` 模型；
- Ubuntu环境将 `.pt` 转换为 `.onnx`，再通过MindSpore Lite的Converter工具转换为端侧 `.ms`（或云端 `.mindir`）模型；面向RK平台另通过RKNN工具链生成 `.rknn` 模型；
- OpenHarmony端侧提供MindSpore Lite与RKNN两种推理引擎，在C++推理代码中适配不同NPU/CPU后端后编译端侧应用；
- 目标硬件为HH-SCDAYU200、RK3568、RK3588等OpenHarmony设备。

### 议题2、construction_path_planning（施工巡检路径规划）技术路线调整
#### 汇报人：高镜宇
**1、仓库更名与定位**

高镜宇说明，路径规划仓更名为 `construction_path_planning`，面向施工巡检机器人，提供从地图接入、目标点下发、全局规划、动态避障、路径跟踪到状态监控的端到端能力，支撑开发者在OpenHarmony终端快速验证自研路径规划算法。

**2、OpenHarmony技术架构**

确定技术架构为：ArkTS + TypeScript业务逻辑 + N-API桥接 + C++17规划/控制算法 + OpenGL ES 2.0渲染 + ROS 2 rosbridge WebSocket通信。各模块划分如下：

| 模块 | 功能说明 | 关键实现 |
| :--- | :--- | :--- |
| 地图与定位接入 | 加载ROS SLAM栅格地图，订阅机器人位姿、激光雷达数据 | rosbridge WebSocket、OccupancyGrid、坐标变换 |
| 巡检任务管理 | 多点航点增删清空、循环次数与停留间隔设置 | Patrol Manager、任务状态机 |
| 全局路径规划 | 生成满足车辆运动学约束的可行路径 | C++17、Hybrid A\*、路径平滑 |
| 动态避障与重规划 | 遇临时堆料、移动机械等动态障碍自动绕行并重规划 | 局部代价地图、动态障碍层、重规划触发 |
| 路径跟踪控制 | 输出速度指令驱动机器人沿路径行驶 | Pure Pursuit、/cmd_vel、速度自适应 |
| 可视化交互 | 地图、路径、位姿、点云、巡检进度实时显示 | OpenGL ES 2.0、ArkTS、手势交互 |
| 状态监控与安全 | 轨迹、电量、速度、连接状态监控，支持急停 | WebSocket状态同步、强制停止、摇杆松手即停 |

**3、验证方式与量化目标**

会议确定“巡检小车初步验证—OpenHarmony终端集成—重新上会”的推进路径，算法已在巡检小车上开展初步验证。量化孵化目标为：路径长度较基准算法（A\*或Dijkstra）缩短 ≥ 10%，单次规划时间 ≤ 100ms，路径曲率标准差 ≤ 0.5，扩展节点数/路径长度比值 ≤ 1.5，多场景规划成功率 ≥ 95%。

于军琪强调，两个仓库均运行于OpenHarmony系统，端侧模型格式、N-API桥接与ArkTS应用必须符合OpenHarmony社区代码规范，README与接口文档要在建仓阶段同步完成。

## 会议决议

1) 两个仓库按算法功能分别命名为 `construction_ai_vision` 与 `construction_path_planning`，纳入openharmony-sig孵化仓统一管理。
2) 施工AI视觉检测仓采用YOLOv5n/v8n/v8s模型，基于MindSpore Lite、RKNN引擎在OpenHarmony边缘设备端侧推理。
3) 施工巡检路径规划仓采用ArkTS + N-API + C++17 + OpenGL ES技术架构，全局规划使用Hybrid A\*，跟踪控制使用Pure Pursuit，经ROS 2 rosbridge与机器人通信。
4) 两个仓库的量化孵化指标作为后续验收依据，未达标不得申请毕业；所有代码须符合OpenHarmony社区规范并通过MR评审。
